# 애드센스 콘텐츠 가치 보강 설계

- 상태: 설계 승인 후 명세 검토 대기
- 작성일: 2026-08-22
- 범위: 홈 생성기 외부 콘텐츠 구조 및 다국어 콘텐츠 품질

## 1. 문제 정의

현재 서비스는 카드 생성 기능은 분명하지만, 검색이나 광고 심사 관점에서 방문자가
얻어 가는 독창적인 정보가 충분히 드러나지 않는다. 홈 화면에 홍보 문구를 더 넣는
방식은 사용자의 제작 흐름을 방해하고, 짧은 문장을 여러 페이지에 반복하는 방식은
콘텐츠 가치를 높이지 못한다.

Google의 공식 기준은 단순한 분량보다 다음을 요구한다.

- 다른 사이트와 비교해 독창적이고 실질적인 가치가 있을 것
- 사용자가 방문하고 다시 돌아올 이유가 있을 것
- 콘텐츠가 주제별로 정리되어 쉽게 탐색될 것
- 복제·반복 콘텐츠, 키워드 나열, 검색엔진용 얇은 페이지를 만들지 않을 것

참고 기준:

- https://support.google.com/adsense/answer/10015918
- https://support.google.com/adsense/answer/10502938
- https://support.google.com/publisherpolicies/answer/11035931

## 2. 목표와 비목표

### 목표

1. FF14 캐릭터 카드 제작에 직접 도움이 되는 고유 콘텐츠를 제공한다.
2. 홈 화면은 카드 편집 작업에 집중하도록 유지한다.
3. `/guide`, `/about`, `/faq`의 역할을 분리하고 서로 중복되는 홍보 문구를 줄인다.
4. 한국어·영어·일본어 콘텐츠가 동일한 정보 구조와 기능 범위를 갖도록 한다.
5. 실제 기능과 일치하는 개인정보·저장·팬 프로젝트 안내를 제공한다.
6. 콘텐츠를 읽은 사용자가 자연스럽게 생성기로 이동할 수 있게 한다.

### 비목표

- FF14 전반의 공략·뉴스·직업 공략 사이트로 확장하지 않는다.
- 검색 키워드 수와 글자 수를 목표로 삼지 않는다.
- 같은 내용을 언어별·URL별로 반복하는 얇은 페이지를 새로 만들지 않는다.
- 홈 편집기와 생성 카드의 시각적 구조를 변경하지 않는다.
- 콘텐츠가 충분히 검토되기 전 광고 영역을 다시 추가하지 않는다.

## 3. 접근 방식

### 선택한 방식: 강한 `/guide` + 역할이 분명한 보조 페이지

새로운 SEO용 페이지를 여러 개 만들지 않고, `/guide`를 카드 제작에 관한 대표
자료로 강화한다. `/about`은 서비스의 정체성과 신뢰 정보를 담당하고, `/faq`는
실제 사용 중 발생하는 문제를 해결하는 페이지로 유지한다.

이 구조는 사용자의 기존 요구인 “홈에서 카드 생성과 무관한 설명 제거”를 유지하면서,
Google이 판단할 수 있는 독창적인 콘텐츠를 한 곳에 집중한다.

## 4. 콘텐츠 정보 구조

### 4.1 홈 `/`

- 카드 생성기와 실제 작성 단계만 노출한다.
- 긴 소개 문단, 기능 홍보 카드, SEO용 반복 문구를 추가하지 않는다.
- 헤더는 사이트명·언어·테마 변경만 유지한다.
- 푸터에서 가이드·소개·FAQ·정책 페이지로 연결한다.

### 4.2 가이드 `/guide`

페이지의 단일 목적은 “이 도구로 공유 가능한 FF14 캐릭터 카드를 완성하는 방법”으로
정한다. 상단에 짧은 소개와 앵커 기반 목차를 두고, 각 섹션은 실제 앱의 입력 항목과
연결한다.

#### 섹션 A — 카드 제작을 시작하기 전에

- 카드가 유용한 상황: 자기소개, 자유부대·공대 모집, SNS 고정 게시물, 지인 공유
- 카드에 담을 정보와 담지 않을 정보를 구분
- 공식 프로필이나 Lodestone 정보를 자동으로 복제하는 도구가 아니라 사용자가
  원하는 시점의 캐릭터 표현을 직접 만드는 도구라는 점

#### 섹션 B — 스크린샷 선택과 크롭

- 캐릭터 얼굴·장비·실루엣이 잘 보이는 화면 선택
- 카드 비율에서 피사체가 잘리지 않도록 여백을 확보하는 방법
- 밝은 배경·어두운 배경에 따른 글자 가독성 확인
- 원본 이미지 해상도와 확대 시 화질 저하의 관계
- 앱의 업로드·크롭 기능으로 확인할 항목

#### 섹션 C — 기본 정보와 자기소개 작성

- 닉네임, 인게임과 다른 이름, 서버·데이터센터를 작성하는 기준
- 주 직업과 직업 레벨을 표시할 때의 의미
- 자기소개를 “무엇을 좋아하는지 / 어떤 교류를 원하는지 / 어떤 활동을 하는지”
  중심으로 쓰는 방법
- 200자 제한에 맞춘 짧은 예시와 피해야 할 개인정보

예시는 특정 사용자의 실제 정보처럼 제시하지 않고, 형식과 작성 원칙을 보여주는
가상 문장으로 표시한다.

#### 섹션 D — 직업과 플레이스타일 표현

- 전투·제작·채집 직업 목록이 카드에서 어떻게 구분되는지
- 주 직업을 하나 정하고 다른 직업은 보조 정보로 배치하는 방법
- 플레이스타일 태그와 자기소개 코멘트의 역할 차이
- 태그를 많이 선택하는 것보다 현재 자신을 잘 설명하는 항목을 고르는 기준

#### 섹션 E — 스타일과 꾸미기

- 폰트 선택 시 글자 모양보다 카드 전체 가독성을 먼저 확인
- 포인트 컬러는 배경과 텍스트의 대비를 해치지 않게 선택
- 스티커는 정보나 분위기를 보완하는 수준으로 사용하고 텍스트를 가리지 않도록
  배치
- 가로형·세로형을 바꾼 뒤 이미지와 스티커 위치를 다시 확인하는 이유

#### 섹션 F — 저장·공유·개인정보

- 카드가 브라우저 안에서 PNG로 생성되는 흐름
- 모바일 인앱 브라우저에서 다운로드가 제한될 수 있는 경우와 해결 방법
- SNS·Discord에 올리기 전 이름·서버·스크린샷에 노출된 정보를 확인하는 체크
- 브라우저 저장 데이터와 다운로드한 PNG의 차이
- 서비스가 SQUARE ENIX와 공식 제휴가 아닌 팬 프로젝트라는 점

#### 저장 전 체크리스트

본문 마지막에 정적인 설명만 두지 않고, 다음 항목을 확인할 수 있는 짧은 체크리스트
UI를 제공한다. 체크 상태는 콘텐츠 서버에 저장하지 않으며 현재 방문 세션 안에서만
동작한다.

- 캐릭터 이미지가 의도한 위치에 있는가
- 닉네임과 서버 표기가 맞는가
- 주 직업과 플레이스타일이 현재 자신을 설명하는가
- 자기소개에 공개하고 싶지 않은 정보가 없는가
- 글자와 포인트 컬러의 대비가 충분한가
- 저장 후 실제 공유 위치에서 읽을 수 있는가

체크리스트는 장식이 아니라 가이드 내용을 실제 제작 행동으로 연결하는 장치로
사용한다.

### 4.3 소개 `/about`

현재의 반복적인 마케팅형 `SEOContent` 블록은 제거하거나 재사용하지 않는다.
소개 페이지는 다음 네 가지 사실만 정확하고 구체적으로 설명한다.

1. 왜 이 도구를 만들었는지
2. 어떤 사용자를 돕는지
3. 어떤 기능을 제공하고 어떤 기능은 제공하지 않는지
4. 이미지 처리·브라우저 저장·팬 프로젝트 범위가 어떻게 되는지

기능 목록을 `/guide`와 같은 문장으로 반복하지 않고, 개발 목적과 서비스 경계를
설명하는 신뢰 페이지로 만든다.

### 4.4 FAQ `/faq`

FAQ는 현재의 실제 문의 중심 구조를 유지한다.

- 저장 오류, 모바일 브라우저, 이미지 화질, 스티커 조작 등 기능별 문제 해결
- 로컬 저장과 개인정보 처리에 대한 정확한 설명
- Lodestone API 미연동, 글로벌 월드, 팬 프로젝트 범위 등 오해 방지
- 관련 답변에는 `/guide#...` 앵커 링크를 연결해 중복 설명을 줄임
- 보이지 않는 FAQ 문구를 만들지 않고, 화면에 표시되는 질문·답변만 구조화 데이터에
  포함

광고나 업데이트 내역을 콘텐츠 가치로 포장하지 않는다.

## 5. 컴포넌트·데이터 설계

현재 `Guide`가 `i18n`의 짧은 문자열 배열을 직접 렌더링하는 구조를 유지하되, 긴
콘텐츠가 커지면 페이지 컴포넌트와 분리된 타입 안전한 콘텐츠 모듈로 이동한다.

예상 변경 경계:

- `src/utils/guideContent.ts`: 한국어·영어·일본어 가이드 본문, 섹션 ID, 체크리스트
- `src/pages/Guide.tsx`: 목차, 섹션, 체크리스트, 생성기 연결 렌더링
- `src/pages/About.tsx`: 소개·신뢰 정보만 남기고 중복 SEO 블록 제거
- `src/components/SEOContent.tsx`: 더 이상 사용하지 않으면 제거하거나 가이드 전용
  컴포넌트로 전환
- `src/utils/faqContent.ts`: 관련 가이드 앵커를 표현할 수 있도록 필요한 경우
  링크 메타데이터 추가
- `src/utils/pageMeta.ts`: 실제 보강된 페이지 목적에 맞게 제목·설명 갱신
- `src/utils/i18n.ts`: 기존 공통 UI 문구와 정책 문구는 유지하되 가이드 본문을
  중복 저장하지 않도록 정리

콘텐츠 데이터가 누락된 언어를 자동으로 다른 언어 문장으로 대체하지 않는다. 개발 중
누락을 즉시 발견할 수 있도록 타입으로 세 언어의 동일한 섹션 키를 강제한다.

## 6. SEO·탐색·신뢰 원칙

- 각 페이지는 하나의 명확한 H1과 목적을 가진다.
- 가이드 목차와 본문 앵커는 실제 존재하는 섹션으로만 연결한다.
- 제목·description에는 실제 페이지가 제공하는 정보만 적는다.
- 언어별 제목과 description은 해당 언어로 작성한다.
- 긴 문장을 여러 페이지에 복사하지 않는다.
- 숨김 텍스트, 키워드 반복, 검색엔진만을 위한 문단을 사용하지 않는다.
- 가이드에서 생성기로 연결되는 CTA는 “카드를 만들고 싶을 때” 자연스럽게 보이는
  위치에만 둔다.
- 기존 FAQPage 구조화 데이터는 실제 표시되는 FAQ와 일치할 때만 유지한다.
- 콘텐츠 보강 후에도 광고는 추가하지 않고, 사용자 경험과 심사 결과를 먼저 확인한다.

## 7. 오류·경계 처리

- 잘못된 가이드 앵커는 생성하지 않도록 섹션 ID를 콘텐츠 데이터에서 함께 관리한다.
- 언어 값이 예상 범위를 벗어나면 기존 기본 언어 처리 방식을 따른다.
- 체크리스트는 새로고침·다른 기기에서 유지되는 기능으로 홍보하지 않는다.
- 브라우저 로컬 저장과 서버 저장을 혼동하지 않도록 문구를 분리한다.
- 이미지·직업 아이콘·폰트의 권리와 팬 프로젝트 고지를 소개·정책 페이지에서
  확인할 수 있게 한다.

## 8. 검증 계획

### 자동 검증

- `npm run lint`
- `npm run build`
- 세 언어 콘텐츠 객체의 섹션 키가 동일한지 타입 검사

### 브라우저 검증

- `/`, `/guide`, `/about`, `/faq`, `/contact`, `/terms`, `/privacy` 직접 접근
- KR·EN·JA 전환 후 가이드 본문·제목·description·FAQ가 같은 구조로 바뀌는지 확인
- 모바일 폭에서 목차·체크리스트·CTA가 가로로 넘치지 않는지 확인
- 체크리스트 상태가 서버 요청 없이 동작하는지 확인
- 콘솔 오류, 깨진 앵커, 누락 이미지, 잘못된 링크 확인
- 홈 카드 작성 UI와 카드 렌더링이 변경되지 않았는지 회귀 확인

### 심사 전 운영 점검

- Search Console URL Inspection에서 홈과 가이드의 Google 렌더링 결과 확인
- Google이 보는 콘텐츠와 사용자가 보는 콘텐츠가 다르지 않은지 확인
- 사이트맵에 실제 존재하는 URL만 남아 있는지 확인
- 콘텐츠 변경 후 충분히 크롤링된 뒤 AdSense 재심사 요청

## 9. 완료 기준

- 홈에 카드 생성과 무관한 장문 홍보 문구가 추가되지 않는다.
- `/guide`만 읽어도 실제 카드 제작을 완료할 수 있는 구체적인 정보가 있다.
- `/about`과 `/guide` 사이에 같은 마케팅 문단이 반복되지 않는다.
- `/faq`는 실제 문제 해결에 집중하고 가이드와 링크로 연결된다.
- KR·EN·JA가 같은 섹션·기능 범위를 제공한다.
- 키워드 나열·숨김 텍스트·검색용 얇은 페이지가 없다.
- 카드 미리보기의 시각 구조와 기존 생성 기능이 유지된다.
- lint·build와 브라우저 검증이 모두 통과한다.
