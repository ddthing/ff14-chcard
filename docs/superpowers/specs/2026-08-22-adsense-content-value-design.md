# 애드센스 콘텐츠 가치 보강 설계

- 상태: B안 설계 승인, 작성 명세 검토 대기
- 작성일: 2026-08-22
- 범위: 홈 외부의 공개 콘텐츠, 검색 크롤링 가능성, 다국어 콘텐츠 품질
- 전제: 카드 내부의 기본 시각 구조와 생성 기능은 변경하지 않는다.

## 1. 설계 판단

기존의 “가이드 문장 보강”만으로는 서비스의 독창성이 충분히 드러나지 않을 수
있다. 현재 서비스가 제공하는 실제 기능을 설명하는 문장만 늘리면 일반적인
마케팅 카피와 비슷해지기 때문이다.

이번 개선은 다음 세 가지를 하나의 경험으로 묶는다.

1. 실제 앱 데이터에 근거한 FF14 카드 제작 참고서
2. 사용 목적에 맞는 카드 작성 도구와 저장 전 점검 흐름
3. 검색엔진이 공개 페이지의 본문을 안정적으로 읽을 수 있는 배포 구조

Google의 공식 기준에서 중요한 것은 글자 수가 아니라 독창적인 정보·경험·분석,
방문자가 다시 찾아올 이유, 명확한 탐색 구조다. 따라서 글자 수를 늘리거나
키워드를 반복하지 않는다.

참고 기준:

- [Google AdSense 사이트 준비](https://support.google.com/adsense/answer/7299563?hl=en)
- [Google people-first 콘텐츠](https://developers.google.com/search/docs/fundamentals/creating-helpful-content)

- [Google 게시자 스팸 정책](https://support.google.com/publisherpolicies/answer/11035931)

## 2. 목표와 비목표

### 목표

1. 이 서비스에서만 얻을 수 있는 카드 제작 기준과 실제 지원 범위를 제공한다.
2. `/guide`를 읽고 바로 카드 작성·저장까지 이어질 수 있게 한다.
3. 홈은 카드 생성 작업에 집중시키고 장문 홍보 문구를 넣지 않는다.
4. `/guide`, `/about`, `/faq`, 정책 페이지의 역할을 분리한다.
5. 한국어·영어·일본어가 같은 정보 구조와 기능 범위를 제공하도록 강제한다.
6. 기본 공개 페이지의 원문 HTML에 핵심 제목과 본문이 존재하는지 빌드 결과로 검증한다.
7. 개인정보·저장 방식·팬 프로젝트 범위를 실제 코드와 일치하게 설명한다.

### 비목표

- FF14 공략, 뉴스, 직업별 공략 사이트로 확장하지 않는다.
- 직업·서버별 SEO 페이지를 대량 생성하지 않는다.
- 사용자 갤러리, 로그인, 댓글, 커뮤니티, 신고 시스템을 추가하지 않는다.
- 단어 수나 검색 키워드 수를 성공 지표로 삼지 않는다.
- 숨김 텍스트, 반복 키워드, 검색엔진 전용 문단을 사용하지 않는다.
- 홈의 카드 미리보기, 카드 내부 기본 정보, 편집 탭 구조를 변경하지 않는다.
- 콘텐츠 검증 전에 광고 영역을 추가하지 않는다.

## 3. 현재 구조 검증 결과

설계는 다음 실제 소스 구조를 기준으로 한다.

| 근거 | 현재 역할 | 콘텐츠에 반영할 원칙 |
| --- | --- | --- |
| `src/data/jobs.ts` | 직업 ID·다국어 이름·역할·아이콘의 단일 목록 | 직업·역할 분류를 본문에 복제하지 않고 데이터에서 표시 |
| `src/data/servers.ts` | 한국·글로벌 지역, 데이터센터, 월드 목록 | 지원 범위를 실제 선택지와 동일하게 표시 |
| `src/contexts/PlayerContext.tsx` | `ff14-playerInfo` 로컬 저장, 용량 초과 시 이미지 제외 fallback | 로컬 저장과 서버 저장을 구분해서 설명 |
| `src/hooks/useImageExport.ts` | 브라우저에서 카드 DOM을 PNG로 렌더링해 다운로드 | “브라우저 내 PNG 생성”을 실제 동작 범위로 설명 |
| `src/App.tsx` | `BrowserRouter`, lazy route, 공개 페이지 경로 | 공개 페이지 사전 렌더링이 필요한지 raw HTML로 검증 |
| `index.html` | React 마운트 전 한국어 fallback과 기본 SEO 메타 | 다국어 페이지가 fallback에만 의존하지 않도록 개선 |
| `src/components/SEOContent.tsx` | 반복적인 기능·마케팅 설명 | 소개 페이지에서 제거하고 사실 기반 콘텐츠로 대체 |

현재 코드에서 확인되지 않은 주장은 콘텐츠에 넣지 않는다. 특히 “모든 기기에서
완벽”, “무한한 커스터마이징”, “개인정보 유출 위험 원천 차단”처럼 범위를 과장하는
문구는 사용하지 않는다. 웹폰트처럼 외부 자원을 불러오는 동작과 사용자의 이미지·
프로필 입력을 별도 서버에 저장하지 않는 동작도 구분해서 검증한다.

## 4. 정보 구조

### 4.1 홈 `/`

- 카드 생성기와 실제 작성 흐름만 유지한다.
- 긴 소개, 기능 홍보 카드, 광고 영역, 업데이트 내역을 추가하지 않는다.
- 헤더는 사이트명·언어·라이트/다크 모드만 유지한다.
- 푸터에서 가이드·소개·FAQ·문의·정책 페이지로 연결한다.

가이드나 소개의 내용을 홈에 요약해 중복 노출하지 않는다. 사용자가 생성기를
열었을 때 바로 입력을 시작할 수 있는 것이 홈의 성공 기준이다.

### 4.2 가이드 `/guide`

페이지의 H1과 단일 목적은 “FF14 캐릭터 카드를 계획하고 완성하는 방법”으로
정한다. 상단에는 짧은 설명과 실제 섹션으로만 연결되는 목차를 둔다.

#### A. 카드의 사용 목적 정하기

세 가지 목적을 실제 입력 필드와 연결해 설명한다.

- SNS 자기소개: 이름, 서버, 주 직업, 플레이스타일, 짧은 코멘트 중심
- 자유부대·공대 모집: 활동 시간, 교류 목적, 주 직업과 보조 직업 중심
- 스크린샷 기록: 이미지, 레이아웃, 포인트 컬러, 스티커의 가독성 중심

각 목적에는 다음만 제공한다.

- 추천 입력 항목과 선택 항목
- 한두 문장으로 된 가상 예시
- 공개 전에 확인할 개인정보 항목

예시는 실제 이용자의 정보처럼 보이지 않도록 “예시”임을 표시하고, 앱의 실제
필드에서 입력 가능한 내용만 사용한다.

#### B. 실제 지원 범위

별도의 직업별·서버별 페이지를 만들지 않고, 한 페이지의 접을 수 있는 참고
섹션으로 제공한다.

- 전투·제작·채집 역할이 카드에서 어떻게 구분되는지
- `src/data/jobs.ts`의 다국어 직업명과 역할을 표시하는 방식
- 한국 서버와 글로벌 서버의 데이터센터·월드 선택 범위
- 주 직업 하나와 선택 직업 목록의 역할 차이
- 수동 입력 방식이며 Lodestone 자동 동기화가 없다는 점

직업명과 월드명은 콘텐츠 파일에 복사하지 않고 현재 데이터 모듈에서 파생한다.
데이터가 변경되면 가이드의 지원 범위도 함께 변경되어 오래된 정보가 남지 않게
한다. 모바일에서는 넓은 표 대신 역할별 카드와 접기/펼치기 구조를 사용한다.

#### C. 스크린샷과 크롭

- 캐릭터의 얼굴·장비·실루엣이 의도한 크기로 보이는 원본을 고르는 기준
- 카드 비율에 맞춰 피사체 주변에 여백을 두는 이유
- 밝은 이미지·어두운 이미지에서 텍스트 대비를 확인하는 방법
- 낮은 해상도 원본을 확대할 때 화질이 떨어지는 이유
- 레이아웃을 바꾼 뒤 이미지 위치를 다시 확인해야 하는 이유

설명은 “예쁜 이미지를 사용하라”에서 끝내지 않고 현재 크롭 UI에서 실제로
확인할 수 있는 행동으로 작성한다.

#### D. 기본 정보와 자기소개

- 인게임 이름과 공개용 이름이 다를 때의 입력 기준
- 서버와 데이터센터를 확인하는 방법
- 주 직업·직업 레벨·플레이스타일 태그의 역할 차이
- 자기소개를 좋아하는 활동, 교류 목적, 활동 시간 중심으로 짧게 쓰는 방법
- 공개하고 싶지 않은 연락처·실명·일정 정보를 입력하지 않는 기준

문장 예시는 짧은 가상 예시만 제공한다. 기본값이나 샘플 문장을 카드에 자동으로
채우지 않는다.

#### E. 스타일과 꾸미기

- 폰트는 장식성보다 작은 카드에서의 판독성을 먼저 확인한다.
- 포인트 컬러는 배경과 본문 텍스트의 대비를 해치지 않게 선택한다.
- 스티커는 분위기나 정보를 보완하되 이름·직업 아이콘·소개 문장을 가리지 않게
  배치한다.
- 스타일을 먼저 정한 뒤 꾸미기를 추가하면 수정 횟수를 줄일 수 있다.

이 섹션은 단순 기능 나열 대신 “언제 사용하고 언제 줄여야 하는지”를 설명한다.

#### F. 저장·공유·개인정보

실제 코드 검증을 거친 다음 아래 범위만 확정적으로 안내한다.

- 카드 PNG 생성이 브라우저에서 실행되는 흐름
- 모바일 인앱 브라우저에서 다운로드가 막힐 수 있는 경우
- `localStorage`에 일부 편집 상태가 남을 수 있고 브라우저 데이터 삭제 시
  사라질 수 있다는 점
- 완성 이미지를 공유하기 전 이름·서버·스크린샷에 노출된 정보 확인
- SQUARE ENIX와 공식 제휴가 아닌 팬 프로젝트라는 점

원본 이미지나 프로필 입력이 외부 서버에 저장되지 않는다는 안내는 네트워크
동작을 확인한 뒤 사용한다. 외부 웹폰트 등 별도로 불러오는 자원은 같은 문장으로
뭉뚱그리지 않는다.

#### 저장 전 점검표

가이드 마지막에는 세션 내에서만 동작하는 체크리스트를 둔다.

- 이미지가 의도한 위치에 있는가
- 이름과 서버가 맞는가
- 주 직업과 플레이스타일이 현재 자신을 설명하는가
- 자기소개에 공개하고 싶지 않은 정보가 없는가
- 글자와 포인트 컬러의 대비가 충분한가
- 실제 공유 화면에서 읽을 수 있는가

체크 상태는 서버나 계정에 저장하지 않으며, 새로고침 후 유지된다고 홍보하지
않는다.

### 4.3 소개 `/about`

현재 `SEOContent`의 마케팅형 블록은 제거한다. 소개 페이지는 다음 네 가지를
사실 기반으로 설명한다.

1. 어떤 문제를 해결하려고 만들었는가
2. 어떤 이용자와 사용 목적을 위한 도구인가
3. 제공하는 기능과 제공하지 않는 기능은 무엇인가
4. 브라우저 처리·로컬 저장·팬 프로젝트 범위는 무엇인가

가이드의 사용법을 다시 붙여 넣지 않는다. 제작자 표시와 문의 경로는 실제 운영
주체와 일치하는지 확인한 뒤 노출한다.

### 4.4 FAQ `/faq`

현재 FAQ의 실제 문제 해결 중심 구조는 유지한다.

- 이미지 저장 실패, 모바일 브라우저, 이미지 화질, 스티커 조작
- 로컬 저장과 개인정보 처리
- 직업·월드 선택, Lodestone 미연동, 글로벌 사용
- 폰트·언어·레이아웃·팬 프로젝트 범위

가이드에서 이미 충분히 설명한 내용을 FAQ에 다시 긴 문단으로 복제하지 않는다.
필요한 항목에는 `relatedGuideSectionId` 같은 메타데이터로 관련 가이드 앵커만
연결한다. FAQPage 구조화 데이터는 화면에 실제 표시되는 질문·답변과 정확히
일치할 때만 유지한다.

업데이트 내역이나 광고 유무를 콘텐츠 가치로 포장하는 질문은 추가하지 않는다.

### 4.5 정책·문의 페이지

`/privacy`, `/terms`, `/contact`는 심사 통과를 위한 장문 콘텐츠가 아니다. 실제
운영·문의·데이터 처리에 필요한 최소한의 정확한 안내로 유지한다.

- 개인정보처리방침: 브라우저 저장, 서버 전송 여부, 외부 자원, 삭제 방법을 실제
  동작과 일치시킨다.
- 이용약관: 팬 프로젝트 범위, 이용 제한, 이미지·폰트 권리 고지를 명확히 한다.
- 문의하기: 버그 제보에 필요한 브라우저·기기·재현 절차를 안내하고 사용자의
  개인정보를 불필요하게 요구하지 않는다.

## 5. 컴포넌트·데이터 설계

콘텐츠와 렌더링을 분리하고, 세 언어가 같은 구조를 갖도록 타입으로 강제한다.

예상 변경 경계:

- `src/utils/guideContent.ts`: 가이드 섹션, 목적별 템플릿, 체크리스트, 설명 문구
- `src/utils/guideReference.ts`: `JOBS`·서버 데이터에서 파생되는 지원 범위 표시값
- `src/pages/Guide.tsx`: 목차, 목적별 템플릿, 지원 범위, 섹션, 체크리스트 렌더링
- `src/pages/About.tsx`: 사실 기반 소개만 렌더링하고 `SEOContent` 제거
- `src/components/SEOContent.tsx`: 사용처가 없으면 삭제
- `src/utils/faqContent.ts`: 필요할 때 가이드 앵커 메타데이터 추가
- `src/utils/pageMeta.ts`: 실제 콘텐츠를 반영한 다국어 title·description 갱신
- `src/utils/i18n.ts`: 공통 UI 문구와 정책 문구만 유지하고 긴 가이드 중복 제거

콘텐츠 객체는 `satisfies Record<Language, ...>` 형태로 작성해 한국어·영어·일본어의
섹션 ID, 목적 템플릿, 체크 항목 수가 누락되지 않게 한다. 한 언어가 빠졌을 때
다른 언어 문장을 자동 fallback하지 않는다.

### 공개 페이지 사전 렌더링

현재 공개 페이지는 `BrowserRouter`와 lazy route 뒤에서 React가 실행된 후 본문이
완성된다. `index.html`에는 React 실행 전 한국어 fallback만 있다. 또한 현재 언어
선택은 URL이 아니라 `localStorage` 상태이므로, 단순 사전 렌더링만으로는 한국어·
영어·일본어를 각각 독립된 검색 URL로 제공할 수 없다. 이를 가능한 것처럼 설명하지
않는다.

검증 결과가 부족하면 다음 경계로 build-time pre-render를 추가한다.

- `/guide`, `/about`, `/faq`, `/contact`, `/terms`, `/privacy`의 기본 한국어 HTML만
  정적으로 생성한다.
- `/`의 카드 편집기는 기존 클라이언트 렌더링을 유지한다.
- 정적 페이지 렌더러는 `StaticRouter`와 서버용 진입점을 사용하고,
  `localStorage`, `window`, `document`를 렌더 단계에서 요구하지 않게 한다.
- Cloudflare Pages의 SPA fallback은 유지하되, 생성된 공개 경로 HTML이 우선
  제공되는지 `dist`와 배포 URL에서 확인한다.
- 동적 렌더링 우회나 검색엔진 전용 HTML을 만들지 않는다. 사용자에게 보이는
  콘텐츠와 크롤러가 읽는 콘텐츠는 동일해야 한다.

사전 렌더링은 콘텐츠 추가와 별개로 검증 가능한 기술 작업으로 취급한다. SSR-safe
경계가 확보되지 않으면 실패한 상태로 배포하지 않고 원인을 먼저 해결한다.

영어·일본어는 우선 동일한 콘텐츠 키·섹션·기능 범위를 타입과 브라우저 검증으로
보장한다. 언어별 검색 유입까지 필요해지면 `/ko/guide`, `/en/guide`, `/ja/guide`
같은 고정 경로와 `hreflang`을 별도 설계한다. 이번 작업에서 URL을 급히 늘려 얇은
번역 페이지를 양산하지 않는다.

## 6. SEO·접근성·UX 원칙

- 모든 공개 페이지는 하나의 명확한 H1과 하나의 목적을 갖는다.
- 가이드 목차와 앵커는 데이터에서 함께 생성해 깨진 링크를 방지한다.
- title·description·canonical은 실제 페이지 내용과 일치한다.
- 언어 선택 후 본문·제목·메타데이터·구조화 데이터가 같은 언어로 전환된다.
- 긴 문단을 여러 페이지에 복사하지 않는다.
- 지원 범위는 모바일에서 가로 스크롤을 강요하지 않는다.
- 접을 수 있는 콘텐츠는 키보드·스크린리더에서 열고 닫을 수 있게 한다.
- CTA는 가이드의 관련 지점에만 두고 방문자를 과도하게 방해하지 않는다.
- 카드 미리보기의 이미지·아이콘·기본 정보 시각 구조는 건드리지 않는다.
- 광고, 업데이트 팝업, 검색엔진용 장식 콘텐츠는 추가하지 않는다.

## 7. 오류·경계 처리

- 데이터 모듈에 없는 직업·월드·역할을 콘텐츠에 하드코딩하지 않는다.
- 데이터가 비어 있거나 형식이 바뀌면 가이드는 깨지지 않고 해당 참고 영역을
  안전한 빈 상태로 표시하며, 개발 환경에서는 오류를 확인할 수 있게 한다.
- 잘못된 가이드 앵커를 만들지 않는다.
- 언어가 예상 범위를 벗어나면 기존 기본 언어 정책을 따른다.
- 체크리스트가 영구 저장되는 것처럼 표현하지 않는다.
- 로컬 저장, 서버 저장, 외부 폰트·자원 로딩을 구분한다.
- 현재 기능이 제공하지 않는 background removal, Lodestone 자동 연동 등의
  내용을 제공하는 것처럼 설명하지 않는다.
- 구조화 데이터가 보이는 콘텐츠와 달라지면 배포하지 않는다.

## 8. 구현 우선순위

### P0 — 사실·중복·크롤링 감사

1. `SEOContent`의 중복·과장 문구 제거
2. 개인정보·저장·PNG 생성·팬 프로젝트 문구를 코드와 대조
3. 공개 경로의 build output raw HTML과 Cloudflare 응답 확인
4. 사전 렌더링 도입 여부를 검증 결과로 확정

### P1-A — 독창적 콘텐츠의 핵심

1. 데이터 기반 지원 범위 참고 섹션
2. 목적별 카드 작성 템플릿 세 가지
3. 실제 편집 단계와 연결된 스크린샷·자기소개·꾸미기 기준
4. 저장 전 세션 체크리스트
5. `/about`의 사실 기반 재작성

### P1-B — 탐색·다국어 품질

1. 가이드 목차와 관련 FAQ 앵커
2. KR·EN·JA 동일 구조 검증
3. page metadata·canonical·구조화 데이터 감사
4. 모바일 접기/펼치기와 키보드 접근성 검증

### P2 — 심사 전 운영 검증

1. 모든 공개 URL 직접 접근 확인
2. raw HTML·렌더된 화면·메타데이터 비교
3. Search Console URL Inspection으로 Google 렌더링 확인
4. 사이트맵의 실제 URL 확인
5. 콘텐츠가 충분히 크롤링된 후에만 AdSense 재심사 요청

사용자 갤러리나 커뮤니티 기능은 이 작업의 결과가 부족할 때 다음 프로젝트로
검토한다. 현재는 로그인·저작권·신고·저장소 운영 부담이 가치보다 크다.

## 9. 검증 계획

### 자동 검증

- `npm run lint`
- `npm run build`
- 세 언어 콘텐츠의 키·섹션 ID·목적 템플릿 구조 타입 검사
- `dist`의 기본 공개 HTML에 각 페이지 H1·핵심 본문·canonical이 존재하는지 검사
- `SEOContent`의 사용처가 남아 있지 않은지 검사

### 브라우저 검증

- `/`, `/guide`, `/about`, `/faq`, `/contact`, `/terms`, `/privacy` 직접 접근
- KR·EN·JA 전환 후 본문·제목·description·FAQ 구조가 동일한지 확인
- 모바일 폭에서 목차·지원 범위·템플릿·체크리스트가 넘치지 않는지 확인
- 가이드 앵커와 FAQ 관련 링크가 정확히 이동하는지 확인
- 체크리스트가 서버 요청 없이 동작하는지 확인
- 콘솔 오류, 깨진 링크, 누락 이미지, 잘못된 언어 fallback 확인
- 홈 카드 입력·미리보기·저장 기능이 변경되지 않았는지 회귀 확인

### 운영 검증

- 배포된 공개 URL의 응답 HTML과 브라우저 렌더링 비교
- Google URL Inspection으로 Google이 읽는 결과 확인
- 콘텐츠와 구조화 데이터가 사용자 화면과 일치하는지 확인
- 광고 영역 없이 사용자 경험과 페이지 품질을 먼저 확인

AdSense 승인 자체는 외부 심사 결과이므로 완료 기준으로 보장하지 않는다. 이 작업의
완료 기준은 “독창적인 실사용 정보가 존재하고, 실제 기능과 일치하며, 검색엔진과
사용자가 같은 콘텐츠를 읽고, 과장·반복·얇은 페이지가 없다”로 정의한다.

## 10. 완료 기준

- 홈에 카드 생성과 무관한 장문 홍보 문구가 없다.
- `/guide`에 실제 데이터 기반 지원 범위와 목적별 작성 기준이 있다.
- 가이드를 통해 입력·크롭·직업·꾸미기·저장 전 확인을 실제로 수행할 수 있다.
- `/about`에 반복 마케팅 문단 대신 제작 목적·범위·한계·처리 방식을 설명한다.
- `/faq`가 실제 문제 해결에 집중하고 가이드와 중복되지 않는다.
- KR·EN·JA가 같은 섹션과 기능 범위를 제공한다.
- 공개 페이지의 핵심 콘텐츠가 build output과 운영 응답에서 확인된다.
- 숨김 텍스트·키워드 나열·직업/서버별 얇은 페이지가 없다.
- 카드 미리보기와 기존 생성 기능이 회귀하지 않는다.
- lint·build·브라우저·raw HTML 검증이 모두 통과한다.
